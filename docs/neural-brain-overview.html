Die Pipeline

Wie funktioniert es?

Von der Markdown-Datei zum semantisch durchsuchbaren Vektor — vollautomatisch im Hintergrund.

1

Vault scannen

Der Scanner liest jede .md Datei, extrahiert Titel, Inhalt, Tags, Backlinks und berechnet einen Content-Hash (SHA-256). Geänderte Dateien werden erkannt, unveränderte übersprungen.

2

Smart Chunking

Lange Notes (≥ 500 Wörter) werden an ## und ### Headings in Chunks gesplittet. Jeder Chunk erhält seinen eigenen Vektor — so findet die Suche den exakten Abschnitt, nicht nur die ganze Note.

3

Embedding & Indexing

Ein multilinguales Sentence-Transformer Modell (MiniLM-L12, 384 Dimensionen) wandelt jeden Text in einen Vektor um. FAISS speichert diese Vektoren für Echtzeit-Suche. FTS5 indexiert den Klartext für Keyword-Matching.

4

Graph aufbauen

Backlinks ([[links]]) werden als Kanten im Graph gespeichert. Zusammen mit automatisch erkannten semantischen Verbindungen entsteht ein Wissensnetz mit 11.000+ Edges.

5

Hybrid Search

Bei einer Suche laufen FAISS (semantisch) und FTS5 (keyword) parallel. Reciprocal Rank Fusion kombiniert beide Rankings zu einem optimalen Ergebnis. Chunk-Treffer zeigen direkt die relevante Sektion.

-- So funktioniert eine Suche unter der Haube --

Vault (.md Dateien)
  → scanner.py     (parsen, hashen, Backlinks extrahieren)
  → chunker.py     (an ## Headings splitten wenn ≥ 500 Wörter)
  → pipeline.py    (Notes + Chunks embedden, Kanten bauen)
  → database.py    (SQLite WAL, FTS5, CAS Versioning)
  → vector_store.py (FAISS IndexIDMap2 FlatIP)
  → retrieve.py    (RRF: FAISS + FTS5 Fusion, Chunk Dedup)
  → server.py      (FastMCP, Tools für Claude)

Technische Details

Die vier Säulen von v2

Jedes Feature im Detail — was es tut, wie es gebaut ist, warum es so funktioniert.

Säule 1

CAS + Versioning

Content-Addressable Storage: Jede Änderung an einer Note wird automatisch versioniert, bevor die neue Version gespeichert wird. Der Vault hat kein Git — CAS ist das Safety Net.

Trigger
Bei jedem upsert_note() wenn sich der Content-Hash ändert
Retention
Max 50 Versionen pro Note, älteste werden automatisch geprünt
Dedup
Kein neuer Eintrag wenn content_hash bereits existiert
MCP Tools
brain_history, brain_diff, brain_rollback
-- Workflow: Note ändern → Version speichern → Rollback --

brain_history("02 Projekte/MeinProjekt.md")
  → [{id: 42, versioned_at: "2026-05-07", reason: ""}, ...]

brain_diff("02 Projekte/MeinProjekt.md", version_id=42)
  → Unified Diff zwischen Version 42 und aktuellem Stand

brain_rollback("02 Projekte/MeinProjekt.md", version_id=42)
  → Schreibt Version 42 zurück in die .md Datei
Säule 2

Smart Chunking

Lange Notes werden intelligent an Markdown-Headings gesplittet. Jeder Chunk bekommt seinen eigenen Vektor — die Suche findet nicht nur die Note, sondern den exakten Abschnitt.

Threshold
≥ 500 Wörter → Split
Split-Punkte
## und ### Headings
Min-Chunk
50 Wörter (sonst merge mit Nachbar)
Vectors
~2500–3500 statt 1847
Säule 3

Hybrid Search + RRF

Zwei Suchsysteme laufen parallel und werden über Reciprocal Rank Fusion zu einem optimalen Ranking kombiniert. Weder rein semantisch noch rein keyword-basiert — beides zusammen.

Semantisch
FAISS Cosine Similarity (384-dim Vektoren)
Keyword
FTS5 BM25 Ranking
Fusion
RRF(d) = 1/(k+rank) mit k=60
Zukunft
Cross-Encoder Re-Ranker ab ~5000 Notes
-- Warum RRF statt gewichteter Scores? --

FAISS Cosine Score:  0.0 — 1.0  (normalisiert)
FTS5 BM25 Score:     0.0 — ???  (beliebige Skala)

→ Scores sind nicht vergleichbar!
→ RRF nutzt Ranks statt Scores
→ RRF_score(note) = 1/(60 + rank_faiss) + 1/(60 + rank_fts)
→ Funktioniert sogar wenn eine Quelle keine Ergebnisse hat
Säule 4

SessionStart Auto-Context

Ein Hook der bei jedem Claude Code Sessionstart automatisch relevanten Vault-Kontext injiziert. Nutzt nur FTS5 (kein Model-Loading) — unter 100ms.

Trigger
Claude Code SessionStart Hook
Query-Aufbau
Git Repo + Branch + letzte 5 Commits
Fallback
Verzeichnisname wenn kein Git
Performance
<100ms (FTS5-only, kein Model)
